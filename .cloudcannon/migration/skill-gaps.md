# Skill gaps — sendit-hugo-template (Hugo + Bookshop) regression run

Paths are relative to `agent-skills/skills/`. Severity: **High** = would break the migration or produce a broken editor experience; **Med** = cost significant time or needed judgment the skill should have given; **Low** = polish.

Run context: Hugo 0.166.0, editable-regions v0.0.21. Single pass. Sectioning thresholds were evaluated and **none tripped** (13 content pages, 0 hardcoded→YAML conversions, 3 collections), so no `plan.md`.

## Gaps

1. **Phase 3/4 ordering breaks the Bookshop build** — Phase 3. `migrate-to-cloudcannon/hugo/content.md` L49–51 (§ Bookshop content) says to rename `_bookshop_name` → `_name` in Phase 3, and its § Verify (L55–57) requires the build to match the pre-migration output. The Bookshop dispatcher (`bookshop_partial "page"`) dispatches on `_bookshop_name`, so after the rename every block renders nothing (or errors) until `cloudcannon-visual-editing/hugo/migrating-from-bookshop.md` (a Phase 4 doc) moves the components and rewrites the calls. **What I did:** moved the components into `layouts/partials/` and replaced the dispatcher with a native `range … partial ._name .` (no region attributes) in Phase 3, leaving the module swap and the `component-library/` deletion for Phase 4. **Fix:** in `hugo/content.md § Bookshop content`, say the rename must land together with "Move components into `layouts/partials/`" and "Rewrite the Bookshop template calls" from `hugo/migrating-from-bookshop.md`, and that region attributes wait for Phase 4. **Severity: Med** (High for an agent that follows it literally: Phase 3's parity gate fails with no guidance).

2. **Page parity against the pre-migration commit is impossible after a required Hugo upgrade** — Phase 5 (and 3). `migrate-to-cloudcannon/hugo/build.md` L8 says to build the pre-migration commit with `hugo -s /tmp/before`. On this site that commit fails on Hugo 0.166 (`resources.ToCSS` removed), exactly as `cloudcannon-visual-editing/hugo/visual-editing.md § Upgrading Hugo first` predicts. Nothing says what the baseline should then be. **What I did:** built "pre-migration commit + upgrade-only fixes" as the baseline (the skill's "build the unmodified site on the target Hugo" step) and compared against that. **Fix:** in `hugo/build.md` L8–9 and `hugo/content.md` L3, define the baseline as the build from § Upgrading Hugo first (unmodified site plus upgrade fixes, on the target Hugo), and tell the agent to save that output in Phase 1. **Severity: Med.**

3. **Existing `cloudcannon.config.yaml` (not `.yml`) isn't anticipated** — Phase 2. `cloudcannon-configuration/SKILL.md` L47 says "if `cloudcannon.config.yml` does not already exist, run `configure generate`". This site has a Bookshop-era **`cloudcannon.config.yaml`**, so that check passes and the CLI writes a second config file (`--dry-run` confirms it targets `cloudcannon.config.yml`). No doc covers extending or replacing an existing config. **What I did:** used `--dry-run` as a reference, renamed the file to `.yml` and rewrote it. **Fix:** check for `cloudcannon.config.{yml,yaml,json,js,cjs,mjs}`; if one exists, run `--dry-run` only and merge. Say whether to keep the existing extension. **Severity: Med.**

4. **`_index.md` URL collapse is "unverified" and the skill makes verifying it a Phase 2 gate** — Phase 2. `cloudcannon-configuration/hugo/collection-urls.md` L23–31 and `hugo/configuration.md` L147 (checklist item "home page and one section list page were opened in the Visual Editor"). This decides whether the home page and `/blog/` open in the editor at all. The agent can't open the editor, and the public docs (placeholder list under "Update the output URL for a Collection") only say `[slug]` is empty for `index`. The Astro "Schemas for index pages" section (`cloudcannon-configuration/astro/configuration.md` L416–437), which the Hugo doc points to, relies on that same collapse. So the "Hugo equivalent" of the Astro pattern rests on an unverified assumption. **What I did:** used `/[full_slug]/`. I moved the one-file `privacy/_index.md` section to `content/privacy.md` so only the two unavoidable `_index` files depend on it, and listed the check for the user. **Fix:** get a definitive CloudCannon answer and document it. Until then, give a known-good fallback (e.g. a `url` front matter key on `_index.md` files with a `{url}`-based pattern, or a separate schema with an explicit URL). **Severity: High** (if it doesn't collapse, the home page and blog listing can't be visually edited; nothing local can detect it).

5. **Data-file-backed *component* regions in Hugo are under-specified** — Phase 4. `cloudcannon-visual-editing/hugo/visual-editing-reference.md` § Data files and `@data` (L151–168) shows only primitive regions inside `{{ with site.Data.footer }}`. The census example (`cloudcannon-visual-editing/astro/visual-editing.md` § Section census, "Header / Navigation" row) calls for `<editable-component data-component="nav" data-prop="@data[navigation]">`. The golden rule (conditional `enable_dropdown`/`enable_nav_btn`, class bindings) requires a component for this navbar. Only one sentence in `hugo/visual-editing-reference.md` L32 ("the editor passes the value at `data-prop` to the partial as `.` — the same shape the build passes") hints that the partial must be refactored to take the data file as `.`, called as `partial "navbar.html" hugo.Data.nav`, with page-dependent logic (active link) moved to `page`. **What I did:** exactly that refactor for navbar and footer. **Fix:** add a worked Hugo example of `<editable-component data-component="navbar" data-prop="@data[nav]">{{ partial "navbar.html" hugo.Data.nav }}</editable-component>`, with the partial reading `.` and using `page` for page context. **Severity: Med** (the obvious reading — wrap the existing `partial "navbar.html" .` — would re-render with a props map where the partial expects a page, and break in the editor).

6. **`<template>` blueprint guidance doesn't cover sub-arrays inside a re-rendered component** — Phase 4. `cloudcannon-visual-editing/visual-editing-reference.md` § When HTML `<template>` blueprints are needed (L211–222): the table has "Page builder" and "Uniform primitive list (no per-item `data-component`)", which says a list that can be empty needs a `<template>`. Every sub-array here (counter numbers, pricing features, FAQ, team…) is a uniform list *inside* a block that is itself re-rendered via `data-component`. Nothing says whether the parent re-render covers "Add item" on an emptied sub-array. The audit also warns (hugo/audit.md L85–86) that a `<template>` shifts `:nth-child`, which matters here (`_counter-up.scss`). **What I did:** authored no templates (assumed the parent component renders new rows) and switched the counter's `:nth-child` to `:nth-of-type` anyway. Listed for user verification. **Fix:** add a row "Uniform list inside a registered component / page-builder block" with a definitive answer. **Severity: Med.**

7. **Generic and Hugo references disagree on where page-builder component attributes go** — Phase 4. `cloudcannon-visual-editing/visual-editing-reference.md` § Where does the registration go (L27): "Inside a page-builder array → `data-editable="component"` on the component's own root element". L279/285: "Array-item wrappers belong in the page template, not in the block dispatcher … CloudCannon wraps each registered component in its own array-item element". `hugo/visual-editing-reference.md` L36–58 puts `array-item` + `data-component` on a dispatcher wrapper `<div>` and forbids them inside the partial. **What I did:** followed the Hugo doc (dispatcher wrapper). **Fix:** make the generic sections SSG-neutral, or say that on Hugo the dispatcher wrapper carries both. "Dispatcher" means different things in the two docs. **Severity: Med.**

8. **Where to put split structure-value files on Hugo is unstated; inline vs split thresholds conflict with the Bookshop doc** — Phase 2. `cloudcannon-configuration/structures.md` L107 (inline for < 5 block types) and L147–171 (split "co-located" `*.cloudcannon.structure-value.yml` files "next to" each component, `_type` as filename prefix). The site has 16 blocks, so split applies. But "next to the component" means `layouts/partials/`, and the doc doesn't say whether that's safe (the editable-regions module bundles `layouts/partials/**`). Names like `home/hero` can't be filename prefixes. The Bookshop example (`cloudcannon-visual-editing/migrating-from-bookshop.md` L47–65) is inline. L336 says the discriminator must match "`componentMap` and `registerAstroComponent`" — Astro-only wording in a cross-SSG doc. **What I did:** `.cloudcannon/structures/content_blocks/<group>/<name>.cloudcannon.structure-value.yml` + `values_from_glob` (validated). **Fix:** add a Hugo row giving the location (`.cloudcannon/structures/…` or `layouts/partials/…` if proven safe) and the naming for grouped `_name` paths. Make L336 SSG-neutral ("matches the partial path on Hugo"). **Severity: Med.**

9. **`site.Data` is deprecated too, and the skill's own Hugo examples use it** — Phase 1/4. `cloudcannon-visual-editing/hugo/visual-editing.md` L51 upgrade table lists only `.Site.Data` → `hugo.Data`. Hugo 0.166 also warns on `site.Data` (it's the same method). `hugo/visual-editing-reference.md` L125, L131, L153–156 and the Hugo troubleshooting table all use `site.Data`. That is a "no new warnings" failure for `hugo/build.md` L7, and `--logLevel info` doesn't name the file. Also unstated: which Hugo the in-editor renderer runs, and so whether `hugo.Data` is safe in bundled partials (I checked: the v0.0.21 WASM embeds Hugo 0.164.0, so it is). **What I did:** replaced `site.Data` in `meta.html`, and passed data files to the re-rendered partials as `.` so they read neither. **Fix:** list `site.Data`/`.Site.Data` together, update the examples to `hugo.Data`, and state the renderer's Hugo version per module release. **Severity: Low–Med.**

10. **Phase 4 readiness gate refers to a census column that doesn't exist** — Phase 1/4. `migrate-to-cloudcannon/SKILL.md` L98: "Every section flagged in the audit census as 'needs editable region'". The mandatory audit census (`migrate-to-cloudcannon/astro/audit.md` § Classifying static pages, template at L18–23 of that section) has no such column, and the Hugo audit defers to it. **What I did:** added a "Needs editable region?" column to the audit census. **Fix:** add the column to the census template, or reword the gate to point at the Phase 4 section census. **Severity: Low–Med.**

11. **Shared-UI footer pattern (`class="contents"`) breaks Bootstrap gutters, and it contradicts the Hugo reference** — Phase 4. `migrate-to-cloudcannon/astro/cc-friendly-conventions.md` § Footer (L76–78) and `cloudcannon-visual-editing/visual-editing-reference.md` L260 recommend a `display: contents` array wrapper for footer columns that sit beside a static logo column. `hugo/visual-editing-reference.md` L67 says "MUST NOT use `display: contents` on the wrapper". The contexts differ (array wrapper vs array-item wrapper), but it reads as a contradiction. On Bootstrap, `.row > *` gives each column its gutter, and a `contents` wrapper would take that `> *` match while removing its own box. The "Hugo equivalent" of the Astro pattern doesn't hold. **What I did:** bound the columns by index (`sections.N.title`) with a real array region on each column's `links`. The by-index fallback is documented in `visual-editing-reference.md` L242. **Fix:** say `display: contents` array wrappers break child-combinator grids (Bootstrap `.row > *`, `grid > *`), point to the index fallback, and make the Hugo L67 rule explicitly about `array-item` wrappers. **Severity: Low–Med.**

12. **Astro audit sub-checklists have no Hugo mapping** — Phase 1. `migrate-to-cloudcannon/hugo/audit.md` L64 sends the agent to `astro/audit.md § Classifying static pages`, "reading `.astro` page as layout with hardcoded sections". That section also contains the "Primitive-vs-computed census" (`{data.x}` interpolations in route files) and the "Frontmatter co-location census" (keyed on `src/cloudcannon/componentMap.ts`, L109–126). Neither maps to Hugo, and the Hugo doc doesn't say whether to skip them. **What I did:** skipped both. Computed values in page templates were handled by the Phase 4 golden rule and partial extraction (privacy). **Fix:** say which sub-checklists apply, or give Hugo forms (`{{ .Params.x }}` in page templates → primitive; `if`/`index`/`where` → extract to partial). **Severity: Low.**

13. **"Legal pages → markdown body" didn't fit this site** — Phase 1. `migrate-to-cloudcannon/hugo/audit.md` L72: "Legal and policy pages → Markdown body in the `pages` collection". Here the privacy page is structured front matter (`privacy[]` of paragraph/bullet sections) that also drives a scroll-spy nav. Converting it to a markdown body would lose the nav. **What I did:** kept the structure as a `legal` schema in `pages`, extracted a `legal/sections` partial and made it a component region. **Fix:** add a row: "Legal page whose layout reads structured front matter → keep the structure as its own schema in `pages`". **Severity: Low.**

14. **`_snippets_imports` guidance assumes the site uses at least one shortcode** — Phase 2. `cloudcannon-configuration/hugo/configuration.md` L27 ("Keep it, and narrow it to the shortcodes the site uses") and `cloudcannon-snippets/hugo/overview.md` L38/L83. The old config had `_snippets_imports: { hugo: true }` and the site uses none. **What I did:** removed the key. **Fix:** "If content uses no shortcodes, omit `_snippets_imports`." **Severity: Low.**

15. **`[relative_base_path]` is defined wrongly** — Phase 2. `cloudcannon-configuration/collection-urls.md` L11 says "file path without extension". CloudCannon's docs say it's the path **excluding the filename**, relative to the collection path. With the skill's definition, `[full_slug]` (`[relative_base_path]/[slug]`, L12) would double the filename. **What I did:** checked the public docs. **Fix:** correct L11. **Severity: Low.**

16. **Author treatment contradicts the data-file shape rule** — Phase 3. `migrate-to-cloudcannon/astro/cc-friendly-conventions.md` L73, L90, L102: `authors.json` "keyed by slug" (`{ "<slug>": {…} }`). `migrate-to-cloudcannon/hugo/audit.md` L37 (and `cloudcannon-configuration/configuration-gotchas.md` rule 3) says like-shaped items must be a top-level array, never a map keyed by slug. **What I did:** n/a here (authors are name-only strings; kept inline). **Fix:** make the author pattern a top-level array with a `slug` field and `value_key: slug`. **Severity: Low.**

17. **Editor-detection timing for page scripts is unstated** — Phase 4. `cloudcannon-visual-editing/visual-editing-reference.md` § Scroll-reveal (L584–586) says count-up and lightbox scripts must early-return under `window.inEditorMode`. It doesn't say whether that flag is set before a `defer`-ed script's `$(document).ready` runs. If it isn't, the guard never fires. **What I did:** guarded `static/js/script.js` and listed it for user verification. **Fix:** state when `window.inEditorMode` is set, or recommend the `.cms-editor-active`/event-based alternative for load-time scripts. **Severity: Low–Med.**

18. **No guidance for text regions inside interactive elements** — Phase 4. FAQ question text sits inside the Bootstrap collapse `<button>`. Nothing covers editable text inside a `<button>` (browser `contenteditable` limits, click-to-toggle collisions). **What I did:** put the region on the `<p>` inside the button and flagged it for verification. **Fix:** a note in § Text editing: for text inside `<button>`/`<summary>`, verify, or bind via the sidebar. **Severity: Low.**

19. **Audit script blind spots on a Bookshop site** — Phase 1. `migrate-to-cloudcannon/scripts/audit-hugo.sh`: it lists partials only from `layouts/partials/`, so the 16 Bookshop components (the real page-builder blocks) don't appear under "Partials". ## What the skills got notably right

- **Hugo upgrade table** (`cloudcannon-visual-editing/hugo/visual-editing.md` L43–64): `resources.ToCSS` → `css.Sass` was exactly the failure, and "build the unmodified site on the target Hugo first" kept it from being blamed on the integration.
- **Audit script** caught the misspelled `hugoVersion` (CloudCannon was silently building on its default Hugo), every Bookshop marker, the JS global bindings and the numbers-as-text risk.
- **Bookshop doc warnings were all true here:** `_structures.content_blocks` had `style: modal` and no `values`; 7 `.bookshop.yml` files had `_inputs.image` naming no field (the fields are `image_path`); blueprint numbers were bare; keeping the grouped `_name` path meant no content values changed.
- **Partial-path components** (`data-component="home/hero"` → `layouts/partials/home/hero.html`), no registration, and the bundle-key local check made verification mechanical.
- **`data-prop=""` for an array inside an array-bound component** (`visual-editing-reference.md` § Empty `data-prop` pass-through) was exactly the privacy-sections case.
- **Scripts that fight editing** (`visual-editing-reference.md` L584–586) named count-up and lightboxes, both present here.
- **`ENV_CLIENT` local build** and the "Processed images │ 0" signal gave a quick, meaningful check. Mixing `config.toml` with a YAML override file worked.
- **Field-completeness rule** (`structures.md` rule 1) found 7 real gaps (counter `prefix`/`suffix`, a header's `no_top_pad`).
- **`[full_slug]`**, "exclude section dirs from `pages`", and "`data_config` for every `@data` name" were all correct, and each is stated once and clearly.
- **Pin a release tag** and **`hugo mod tidy`** worked first time: the WASM fetched and Bookshop dropped out of `go.mod`/`go.sum`.
